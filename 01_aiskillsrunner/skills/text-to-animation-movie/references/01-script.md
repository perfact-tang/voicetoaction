# 从文本到台词：自然口播讲解写法

## 1. 核心目标：像真人在面对面聊天，而不是念 PPT 提纲

好的知识讲解动画，台词听起来应该像**一位懂行的朋友在白板前娓娓道来**：
有痛点共鸣、有大白话解释、有具体例子、有承上启下的自然过渡、有客观的优缺点权衡。

**绝对要避免的「机械感」通病：**
- ❌ **PPT 金句/口号体**：一句一个硬断言（如「文字是一维的，画面是二维的，顺序不能反」），听起来像背课文或播报提纲。
- ❌ **干瘪下定义**：上来就背概念定义，不先说「这东西到底解决什么麻烦」。
- ❌ **硬切转场**：上一场刚说完 A，下一场毫无铺垫直接跳到 B，观众脑子跟不上。
- ❌ **每句都很短且收句号**：TTS 在每个句号处重新起调，听起来一顿一顿「蹦字」。

## 2. 黄金口播叙事结构（先拆骨架，再写台词）

收到原文后，**不要按原文小标题逐段翻译**。先在 `$DOC_DIR/分镜.md` 里把原文拆成以下四段式骨架：

### ① 开篇钩子：场景带入 + 问题串 + 一句话承诺（1–2 场）
- 从观众日常工作或生活里**真会碰到的场景**起手（「现在做……经常会碰到……」「我们平时写……常常会遇到……」）。
- 连续抛出 **2–3 个具体选择困境或痛点问题**（「如果只是想……应该用哪个？如果……又该怎么选？尤其是……到底是不是一回事？」）。
- 最后给一个干脆的承诺（「这个视频我们就把这几种……放在一起，从原理到应用场景一次讲清楚。」）。

### ② 核心模块展开：每个概念走「六步口播循环」（主体部分）
讲清楚任何一个概念、方法或方案，按下面这个最符合人脑理解习惯的顺序走：
1. **先说具体痛点**：不急着抛名词，先描述现实麻烦（「我们平时收藏的文章、写的笔记，往往散落在各种文件夹里，时间一长，自己都不一定记得存在哪里……」）。
2. **一句话说人话**：用通俗的话给它定性（「简单来说，就是让 AI 帮我们整理资料，把零散的内容变成一套可以持续更新的知识库。」/「你可以简单理解为：先……再……」）。
3. **拆结构或步骤**：讲清内部怎么运转（「这个结构其实不复杂，主要有三个部分：……」「整个过程分成两步。第一步……第二步……」）。
4. **立刻举具体例子**：把抽象机制落到有画面感的真实场景里（「举个例子，员工问公司的差旅报销标准是多少，系统可以从员工手册里找到对应的规定……」「假设现在有两个文档：第一份记录项目 A 使用了检索服务，第二份记录……」）。
5. **点出优势与适用场景**：说明它适合干什么（「它的优势是……所以如果你只是……它就是一个很合适的选择。」）。
6. **客观指出局限，自然引出下一个**：用当前方案的边界，顺理成章引出下一个概念（「但它也有一个局限：如果……单纯依靠……就可能不够用了。这时候就可以考虑……」）。

### ③ 澄清易混淆点（1 场，可选但极加分）
如果主题里有容易搞混的两个概念，专门给 1 场做**一句话对比点破**：
- 「这里还有一个容易混淆的地方，就是 A 和 B。虽然它们都能……但底层完全不是一回事。一个是把……连接起来，一个是把……组织起来。」

### ④ 务实收尾：场景对照 + 组合落地 + 选型判断（1–2 场）
- **不要**写成「总之，以上就是今天的全部内容，感谢观看」的套话。
- 用「如果你……可以考虑 A；如果你……通常 B 就够用了；如果……就可以考虑 C」把全文收成一张清晰的选择地图。
- 最后落在一个**务实、克制、可执行的判断**上（「所以选型最重要的不是哪个技术更新、更热门，而是先搞清楚自己的数据是什么、需要 AI 回答什么问题，再决定用哪种技术，或者怎么组合。」）。

## 3. 自然口语衔接词库（让台词「流动」起来）

鼓励使用自然、克制的口语衔接，把相邻场景串成一整段连贯的讲述：

| 作用 | 推荐的自然口语表达 |
|---|---|
| 开场破冰 | 「现在做……经常会碰到……」「我们先从……说起。」 |
| 说人话定性 | 「简单来说，就是……」「你可以简单理解为：先……再……」 |
| 拆解结构 | 「这个结构其实不复杂，主要有三个部分：……」「整个过程分成两步。」 |
| 举具体例子 | 「举个例子，……」「我们还是用……举例子。假设现在有……」 |
| 递进补充 | 「而且不只是用来……，我们还可以在里面……」「生成……以后，你再……」 |
| 指出局限 | 「但它也有一个局限：如果……就可能不够用了。」「但很明显，你还需要额外做……」 |
| 自然切题 | 「这时候就可以考虑……」「接下来切换到……场景。」「前面……主要是解决……，但还有一个更复杂的需求：……」 |
| 收束对照 | 「最后，我们把这几种……放在一起看。」「这里还有一个容易混淆的地方……」 |

## 4. 正反例对比 & 风格标杆

### ❌ 反例（生硬机械、PPT 提纲味）
```jsonc
["L01", "RAG 是检索增强生成技术。"],
["L02", "它包含入库和检索两个核心步骤。"],
["L03", "普通 RAG 存在跨文档检索的局限性。"],
["L04", "GraphRAG 通过知识图谱解决了这一问题。"]
```
问题：全是冷冰冰的书面陈述句，没有场景、没有例子、没有过渡，读出来像机器人在念百科。

### ✅ 正例（自然口播、层层推进、有例子有过渡）
```jsonc
// S05: rag_intro
["L09", "接下来切换到企业场景，公司有几千份文档，"],
["L10", "员工想查一条报销规定，怎么让 AI 快速找到**准确信息**？"],
["L11", "这就是 **RAG** 最典型的应用场景。"]

// S06: rag_flow
["L12", "你可以简单理解为：先让 AI **找资料**，再根据找到的资料回答问题。"],
["L13", "整个过程分成两步：第一步把文档切分向量化入库，第二步按问题检索最相关片段。"]

// S07: rag_limit
["L14", "它的优势是技术成熟、检索快，适合企业内部问答，"],
["L15", "但它也有个局限：如果答案需要把**好几篇文档**串起来，普通 RAG 就不够用了。"]
```

### 风格标杆片段（学习这种语感与节奏）
> 先从个人知识管理说起。我们平时收藏的文章、写的笔记，还有项目里积累的经验，往往散落在各种文件夹和文档里，时间一长，自己都不一定记得存在哪里。每次打开一个新的 AI 对话，还得重新给它介绍背景，之前积累的东西很难直接用起来。LLM Wiki 就是为了解决这个问题。简单来说，就是让 AI 帮我们整理资料，把零散的内容变成一套可以持续更新的知识库。
> ……
> 举个例子，员工问公司的差旅报销标准是多少，系统可以从员工手册里找到对应的规定，再让 AI 根据原文组织答案，甚至把引用来源一起返回。这就是普通 RAG 的基本工作方式。它的优势是技术比较成熟，检索速度快，也能处理大量文档。但它也有一个局限：如果用户问的不是某一篇文档里的具体内容，而是需要把好几篇文档中的信息串起来，单纯依靠文本相似检索就可能不够用了。这时候就可以考虑 GraphRAG。

## 5. 分场节奏、字数与字幕高亮规范

### 以「意群」为单位分场（长短交替，有呼吸感）
- **不要机械地每场死卡 1 行 25 字**。按「一个完整的视觉意群」来分场：
  - **短场（抛问题 / 关键转折 / 结论定调）**：1–2 行，约 25–45 字（6–10 秒）。
  - **展开场（讲原理步骤 / 举具体例子 / 对比分析）**：2–3 行，约 45–80 字（10–18 秒）。
- **单行字幕长度**：控制在 **16–32 字**（保证在 9:16 竖屏下 1–2 行清晰展示，不挤占插图空间）。
- **全片时长参考**（按 **4.2 汉字/秒** 估算）：
  - 常规 2–3 分钟讲解：约 550–850 汉字，12–18 场。
  - 深度 3–5 分钟讲解：约 850–1350 汉字，16–24 场（`build_audio.py` 上限为单场 24s、全片 360s）。
  - 若指示文指定了「控制在 N 分钟」，按 4.2 汉字/秒反推字数。

### 连贯性与标点（让 TTS 读出真人语调）
配音是**按场景连读**的：同一场的 1–3 行会拼成一段话送进 TTS。
- 场内相邻两行如果是同一句的延续，行尾用 `，`；如果是问句可以保留 `？`（TTS 读问句的自然上扬很加分）；只有一场结束用 `。` / `？`。
- **合理使用 `**关键词**` 触发荧光笔高亮**：
  - 每行最多标 **1–2 个**真正核心的概念词或转折词（如 `**RAG**`、`**准确信息**`、`**好几篇文档**`）。
  - 渲染时字幕卡会对 `**...**` 播放流畅的荧光笔扫过动效；`build_audio.py` 在送入 TTS 和生成 `.lrc` 前会自动剥离 `**`，**不会**读出星号。
- 英文专有名词（RAG / GraphRAG / LLM Wiki / Ontology / Agent / Function Call）保留原文，不要硬译；数字用阿拉伯数字。

### 与画面的分工
**台词负责「娓娓道来」，画面负责「把逻辑结构立起来」。**
- 台词在举「客户—订单—商品」的例子时，画面就画出三个带图标的 `GraphNode` 和 `FlowArrow` 关系连线，而不是把一整段台词抄进方框里。
- 台词在对比四种技术怎么选时，画面就排出四张带 `Icon` 和 `PillBadge` 的 `PaperCard` 对照卡。

## 6. 场景 ID 与视觉 ID

- 场景 ID：`S01`、`S02`…（两位数字）
- 台词 ID：`L01`、`L02`…（全局唯一且连续）
- 视觉 ID：小写英文蛇形/单词，一眼看出这一场画什么（如 `hook_questions`、`wiki_structure`、`rag_pipeline`、`graphrag_hops`、`ontology_model`、`compare_four`、`takeaway`）。

## 7. 写完之后的节奏自检

```bash
cd "$DOC_DIR/engine"
python3 scripts/build_audio.py --dry-run
```

逐项确认：
- [ ] 大声默读一遍台词：是否像真人在白板前聊天讲解？有没有生硬的 PPT 提纲味？
- [ ] 每个抽象概念是否都有「大白话定性 + 具体例子」？
- [ ] 场景之间是否有自然的承上启下过渡？
- [ ] 是否合理使用了 `**关键词**` 高亮（每行 0–2 处，不过度堆砌）？
- [ ] `--dry-run` 无 `!! over budget` 且无 `<-- too long`（单场 ≤ 24s、总长 ≤ 360s）
- [ ] `script.json` 里每个 `visual` 都将在 `src/scenes.tsx` 的 `VISUALS` 中实现
