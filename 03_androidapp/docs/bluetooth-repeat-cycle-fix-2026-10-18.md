# 重复激活后挂断失效与开始播报修复

## 结论与证据边界

确认代码存在会影响重复操作的状态与清理缺陷，已针对性修复；尚不能把用户遇到的每次挂断失效都归因于旧资源残留。

最近保留下来的两轮日志（10 月 17 日 23:50、23:52，日本时间）显示，第二轮确实建立了新的 Telecom 通话，蓝牙栈向眼镜公布了 `numActive=1`，并接通 SCO 麦克风。该轮从开始到 `ACTION_STOP` 结束，没有捕获 `EVENT_TYPE_HANGUP_CALL`、`BT - hanging up call` 或应用 Telecom 结束回调。故这两轮不能解释为“挂断回调已进应用但仅被工作流丢弃”，也没有证据证明旧通话对象直接阻止了新通话建立。先前成功轮的完整日志已经不在手机滚动缓冲区中，无法还原每一次操作。

原始证据：[应用日志](logs/huawei-repeat-before-fix-app-2026-10-17.log)、[蓝牙栈摘录](logs/huawei-repeat-before-fix-system-2026-10-17.log)。此前纯诊断已经证明至少一次眼镜 HFP 挂断指令能进入应用，见 [纯触控实验](huawei-touch-probe-results-2026-10-17.md)。

## 确认的代码缺陷及修复

- 旧实现的全局 `activeConnectionReady` 只在创建/销毁时清空，实际端点离开蓝牙或 SCO 断开时仍可能为真。改为每轮独立会话，经典 SCO 必须同时具备已附加连接、蓝牙端点和已连接音频；路由变化立即更新。蓝牙音频监听使用 application context，不依赖媒体控制服务是否仍存活。
- 旧通话请求、失败回调和控制回调没有完整的轮次身份。每次 `placeCall` 传递独立 session id 并绑定 recording id；取消后的迟到连接、旧端点与销毁通知不能清空或接管新一轮。通话对象的创建、状态变更和销毁统一在主线程执行。
- 挂断原来进入通用“触发/确认”入口，重复回调有机会被理解为上传确认。现在通话结束只针对所属录音生效，并且每轮只接受一次；保存中、上传确认中、已空闲或其他录音的旧回调都忽略。上传仍需要新的媒体确认。
- `StartingRecording` 虽有到期时间，但原触发逻辑没有使用；若准备一直未完成，后续按键会持续被忽略。到期后可重新唤醒，旧准备协程会取消，并在关键异步边界核对当前录音身份。
- 缺少 `onConnectionServiceFocusLost` 的资源释放与回执。现在请求收尾录音，待资源释放后调用 `connectionServiceFocusReleased()`；新一轮重新获得焦点会使旧轮的等待回执失效，避免迟到清理干扰新轮。Android 文档说明未在五秒内回执可能导致服务被系统断开；这是已确认的实现遗漏，但旧版未记录焦点回调，不能证明它就是上述两轮无 HFP 指令的唯一原因。
- 正常通话控制不再把旧连接 `setActive()` 作为下一轮复用。结束后销毁，再为下一次录音建立新连接；上传确认前等待媒体输出恢复，最多三秒。未恢复时保留文件并提示在手机上传，不在无可用媒体通道时继续确认倒计时。
- 监测 SCO 音频断开，短暂重连恢复后取消失效处理；仍断开时只对对应录音停止并保存已有内容，不自动切换手机麦克风。安静或 PCM 全零本身不是停止依据。
- 恢复“开启录音”：启动参数原来仍传递，但服务中的播报调用已删除。现在实际路由与录音状态确认后，异步播报短句；立即开始收音，不等语音结束，排队结束请求优先。

官方依据：[ConnectionService 的焦点释放和连接生命周期](https://developer.android.com/reference/android/telecom/ConnectionService)、[HFP 音频连接状态](https://developer.android.com/reference/android/bluetooth/BluetoothHeadset)。
